# The trust ledger

One file listing **everything outside our direct control that vbm-sse executes or depends on**: code we did not prove, code we did not write, and facilities we assume. It exists because verified by construction is the first priority: the size of the unverified base and the handling of its boundary is the most critical measure. A boundary with no entry here does not land (`scripts/trust-ledger-check.sh`, Tier 1). The pattern is the one of [vbm-json](https://github.com/witt3rd/vbm-json); only the derivation of the required set differs.

**Snapshot at the first landing:** the specification and the incremental machine are pure Lean over `Init`; there is **no C, no runtime shim, no loader and no extern** yet. The closure of the one entry point, `LeanSse.feed` (`scripts/closure-entries.txt`), is `LeanSse` plus `Init`. The ledger below covers what the *build* depends on. The trusted pieces that arrive with the C and WebAssembly targets (the freestanding runtime, the C interface, the loaders, the language toolchains) are listed under "Planned" and move up into numbered entries in the landing that adds each one.

## How the gate keeps this file true

The set of things that must appear here is **derived from the tree, not from this file**: every `@[extern]` symbol in `LeanSse/`, every file under `runtime/*.c` and `abi/*.c`, every hand-written binding loader, every `.github/workflows/` file, the build pins (`lean-toolchain`, `mise.toml`, `lakefile.lean`), the Lean pin's compiler, runtime and bundled clang/ld.lld (the keys `lean-compiler`, `lean-runtime`, `clang-lld`), every closure module that is neither `LeanSse` nor `Init` (`scripts/ClosureGate.lean --emit`), and a watch-list of tools the scripts run. Each is a key (`file:`, `extern:`, `module:`, `tool:`, plus the three Lean keys) that an entry must name on its **Covers** line.
- A new boundary (extern, C file, loader, workflow, tool) with no entry **fails**. Moving code between closure classes does not remove it from the required set.
- A `Covers` key that names nothing real fails (a stale or invented cover), and **removing any entry fails** (the gate does this to itself on every run, one entry at a time: an entry that covers nothing required is padding). Dangling file references fail. An entry needs all seven fields, a **Plan** from `verify | replace | sandbox | accept`, and `accept` needs `because ...`. **Assumes** must link a written contract or say `no written contract` (counted as a gap); **Test** must name a test that can fail or say `none` (counted as a gap).
- Not covered by the gate (say so rather than pretend): a tool called from a script that is not on the watch-list in `scripts/trust-ledger-check.sh`, and the *quality* of an entry's prose.

The count printed on every run and in the Tier 1 log `scripts/land-direct` keeps: `trust ledger: N entries (... gaps)`.

Entry format: **What** it is; **Enters** where it enters; **Assumes** what we assume of it (the contract); **Test** the test that can fail; **Owner**; **Plan**.

## The Lean toolchain (pinned: 4.35.0, one Lean release for the whole tree)

### T01. The Lean compiler: frontend, kernel, C emitter
- **What:** the `lean` release pinned in `lean-toolchain` and `mise.toml`: the elaborator, the kernel that checks every proof, and `EmitC`, which will turn our definitions into the C that becomes the portable artifact. A kernel soundness bug would void the proofs; an emitter bug would give the C different semantics from the Lean. Nothing proves the emitter preserves semantics.
- **Enters:** `lean-toolchain`, `mise.toml`; every `.lean` file.
- **Assumes:** the kernel is sound and `EmitC` is faithful: no written contract beyond Lean's own documentation. The shared vectors (generated by the Lean reference, to be run in every binding) are the check on the emitted code; `leanchecker` and nanoda are the checks on the kernel (T02).
- **Test:** scripts/tier2.sh (leanchecker `--fresh`, nanoda); the emitter is checked only by the vectors, which arrive with the C interface (none yet).
- **Owner:** upstream Lean (leanprover/lean4); the owner pins it (CODEOWNERS: `lean-toolchain`, `mise.toml`).
- **Plan:** accept, because there is no other mature route from Lean to C, WebAssembly and the other targets and the kernel is small and independently re-checked; revisit when an extractor with a semantics-preservation proof exists.
- **Covers:** `lean-compiler` `file:lean-toolchain` `file:mise.toml`

### T02. The independent proof checkers: leanchecker, nanoda
- **What:** `leanchecker --fresh` replays every declaration in a fresh environment (guards a tampered or stale `.olean`); nanoda (`nanoda_bin`, shipped in the Lean release) re-checks the exported proof with an independent kernel implementation.
- **Enters:** `scripts/tier2.sh` (run by CI after merge); they read the build products and the `leanexport` of `LeanSse` and `LeanSseProofs`.
- **Assumes:** that two independent checkers agreeing is evidence the kernel did not mis-accept; no written contract.
- **Test:** `scripts/tier2.sh` is the test; no negative test of the checkers themselves exists here (a corrupted export that nanoda must reject is planned).
- **Owner:** upstream Lean; the owner approves the tier script (CODEOWNERS via the protected set).
- **Plan:** verify. Add a negative self-test (a corrupted export must fail nanoda).
- **Covers:** `tool:leanchecker` `tool:nanoda`

### T03. The Lean runtime and its headers (lean.h, libleanrt)
- **What:** the C runtime every Lean-emitted C file links: reference counting, allocation, arrays and strings, big numbers (`lean.h`, `libleanrt`). It is the lowest layer under the library's compiled code, in every binding. It is not checked by us.
- **Enters:** the Lean release pinned in `lean-toolchain`; the emitted C of `LeanSse` will include `lean.h`; for WebAssembly and the freestanding build a small runtime shim will replace the allocator (Planned P1).
- **Assumes:** the runtime implements Lean's object model correctly; no written contract.
- **Test:** none of ours: it is exercised only through the vectors (none yet).
- **Owner:** upstream Lean; the owner pins the version.
- **Plan:** accept, because the runtime is part of the one Lean release we pin and no verified replacement exists; keep the closure `Init`-only so the part of it that runs is small (`scripts/ClosureGate.lean` forbids `Std` and `Lean` in the exports' closure).
- **Covers:** `lean-runtime`

### T04. clang and ld.lld (the compiler and linker the Lean release bundles)
- **What:** the C compiler and linker bundled in the Lean release (`bin/clang`, `bin/ld.lld`), used by `lake` and `leanc` to compile Lean's emitted C into objects and static libraries, and later to produce the WebAssembly module and the shared libraries. A miscompile here changes the program the proofs were about.
- **Enters:** `lean-toolchain` (the bundle comes with the pin); `lakefile.lean` (every `lean_lib` build).
- **Assumes:** the compiler preserves C semantics for the emitted code; no written contract.
- **Test:** none of ours today; the vectors run against the compiled artifact, which is the real check (none yet).
- **Owner:** upstream LLVM via the Lean release; the owner pins it.
- **Plan:** sandbox. Check the compiled artifact against the reference with the shared vectors in CI, never trust the compile; no replacement is planned.
- **Covers:** `clang-lld`

## The build and process tools

### T05. Lake and the build file
- **What:** `lake` (shipped in the Lean release) reads `lakefile.lean` and builds both libraries; the file sets `warningAsError` and `autoImplicit false` and declares the two module roots (`LeanSse`, `LeanSseProofs`), the first `Init`-only.
- **Enters:** `lakefile.lean`; every `lake build` and `lake env lean --run` in `scripts/`.
- **Assumes:** the build builds the files that are in the tree and nothing else; the root split and the `Init`-only rule are enforced by Tier 1, not by Lake (`scripts/tier1.sh`: the import scan).
- **Test:** scripts/tier1.sh (zero-warning check with its negative case; the import scan with its negative cases).
- **Owner:** the owner (CODEOWNERS: `lakefile.lean`).
- **Plan:** accept, because Lake is the Lean toolchain's own build tool and a change to it is a toolchain change (T01).
- **Covers:** `file:lakefile.lean` `tool:lake`

### T06. mise: installs the pinned Lean release
- **What:** `mise` downloads and installs the Lean release tarball named in `mise.toml` from GitHub releases and puts it on `PATH` for `mise exec -- ...`.
- **Enters:** `mise.toml`; every script is run as `mise exec -- scripts/...`.
- **Assumes:** the tarball is the one released for that tag; no checksum is verified by us today (no written contract): this is a supply-chain gap.
- **Test:** none: nothing here can fail if the tarball were swapped (a gap, counted).
- **Owner:** the owner (`mise.toml` is in the protected set); mise is upstream.
- **Plan:** sandbox. Pin the release checksum in `mise.toml` (a lockfile) once the CI exists; until then the tarball's integrity is GitHub's.
- **Covers:** `tool:mise`

### T07. git, gh, flock, python3, cargo and the vendored lander: the process tooling
- **What:** `git` and `gh` (the red-check and the rebase and push steps of `scripts/land-direct`), `flock` (the lander's mutex), `python3` (the trust-ledger checker, the scrub gate, the workflow lint). The lander is a pinned copy of vbm-land (`scripts/land/`), which names `cargo` only in an example configuration it ships. They run on the developer's machine and in CI; none is part of any artifact.
- **Enters:** `scripts/land-direct`, `scripts/land/`, `scripts/trust_ledger.py`, `scripts/scrub.py`, `scripts/trust-ledger-check.sh`, the Tier 1 scripts.
- **Assumes:** they do what their manuals say; the self-tests of the scripts that use them (scratch repositories, a `gh` shim) are the check that our use of them is right; no written contract.
- **Test:** scripts/test_land_direct.sh, scripts/test_protected_set.sh, scripts/test_githook.sh (each runs the real script against a scratch repository).
- **Owner:** upstream tools; the owner approves the scripts (protected set).
- **Plan:** accept, because they touch the process and not the artifact: a compromised tool could land a bad change, which the gates and the owner's review of protected paths are there to catch.
- **Covers:** `tool:git` `tool:gh` `tool:flock` `tool:python3` `tool:cargo` `tool:wt`

### T08. The CI runner and workflow actions (GitHub Actions)
- **What:** `.github/workflows/core.yml` runs `scripts/tier1.sh` on every push to `main`, and `scripts/tier2.sh` every 6 hours (schedule) and on manual dispatch, on GitHub-hosted `ubuntu-latest` runners only (never self-hosted: `scripts/lint-workflows.py` fails Tier 1 on a self-hosted label, on a `pull_request_target` trigger and on any secret other than the default token). The workflow has no pull-request trigger, so a fork's code never runs with the repository's token. vbm-land's own scheduled-update workflow is not installed (it uses secrets and an unpinned action): the online drift check of the pinned lander (`scripts/land/bin/land-check --upstream`) runs in Tier 2. Third-party actions are pinned by commit sha (a comment names the tag): `actions/checkout`, `actions/cache` (restores `.lake`) and `jdx/mise-action` (installs mise and the pinned Lean). Token: the default `GITHUB_TOKEN`, `contents: read`; no secrets.
- **Enters:** `.github/workflows/`; every Tier 1 and Tier 2 run in CI. The workflows run only on GitHub: they cannot be run here.
- **Assumes:** the runner image, the pinned action commits and the cache behave as documented; a cache hit is only a speed-up (Tier 1 rebuilds with zero warnings and the gates re-derive everything), but a poisoned cache or a compromised upstream action could change what is checked. No written contract beyond GitHub's documentation: the lander's own rules (`docs/decisions/0002-land-direct.md`) read the `tier1` job as the definition of a red main.
- **Test:** none that can fail inside this repository (the workflows cannot run locally); the check that a workflow exists and is covered here is `scripts/trust-ledger-check.sh` (a `.github/workflows/*` file with no entry fails Tier 1), and `scripts/lint-workflows.py` with `scripts/test_lint_workflows.sh` checks their structure.
- **Owner:** the owner (`.github/workflows/` is in the protected set and CODEOWNERS); the actions are upstream (GitHub, jdx).
- **Plan:** sandbox. Keep the permissions read-only and secret-free; the actions are pinned to commit shas; the cache never replaces the gates.
- **Covers:** `file:.github/workflows/core.yml`

## Planned (not in the tree yet; promoted to a numbered entry, with a derived key, in the landing that adds the file)

These are written down now so the trust base is known before the code exists. They are **not gated** until their file lands; the landing that adds the file must add the entry (the derivation in `scripts/trust-ledger-check.sh` then requires it).

- **P1. The freestanding runtime (`runtime/rt.c`).** The allocator and `mem*` shim of the WebAssembly and native builds, shared with vbm-json's (`vbm-rt` when it is extracted).
- **P2. The C interface (`abi/`, `include/vbm_sse.h`).** Chunk in, events out, caller-owned buffers; a described ABI checked against the header.
- **P3. Each binding's loader and generated readers.** Types and FFI declarations are generated from the ABI description and counted as boundary; a hand loader decides nothing.
- **P4. The per-language toolchains (Node, rustc, CPython) in CI.** The runners and package registries are outside our control.
