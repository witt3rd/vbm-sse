# The trust ledger

One file listing **everything outside our direct control that vbm-sse executes or depends on**: code we did not prove, code we did not write, and facilities we assume. It exists because verified by construction is the first priority: the size of the unverified base and the handling of its boundary is the most critical measure. A boundary with no entry here does not land (`scripts/trust-ledger-check.sh`, Tier 1). The pattern is the one of [vbm-json](https://github.com/witt3rd/vbm-json); only the derivation of the required set differs.

**Snapshot:** the specification, the incremental machine and the array machine are pure Lean over `Init`; there is no `@[extern]`. The three Lean exports the C interface calls (`LeanSse.abiNew`, `abiFeed`, `abiReport`; `scripts/closure-entries.txt`) have a closure of `LeanSse` plus `Init`. The trusted pieces around them are the C interface (T09), the freestanding runtime (T10), the hand-written loaders of the bindings (T11) and the tools of the C, WebAssembly and binding builds (T12), besides the build entries (T01 to T08).

## How the gate keeps this file true

The set of things that must appear here is **derived from the tree, not from this file**: every `@[extern]` symbol in `LeanSse/`, every file under `runtime/*.c` and `abi/*.c`, every hand-written binding loader, every `.github/workflows/` file, the build pins (`lean-toolchain`, `mise.toml`, `lakefile.lean`), the Lean pin's compiler, runtime and bundled clang/ld.lld (the keys `lean-compiler`, `lean-runtime`, `clang-lld`), every closure module that is neither `LeanSse` nor `Init` (`scripts/ClosureGate.lean --emit`), and a watch-list of tools the scripts run. Each is a key (`file:`, `extern:`, `module:`, `tool:`, plus the three Lean keys) that an entry must name on its **Covers** line.
- A new boundary (extern, C file, loader, workflow, tool) with no entry **fails**. Moving code between closure classes does not remove it from the required set.
- A `Covers` key that names nothing real fails (a stale or invented cover), and **removing any entry fails** (the gate does this to itself on every run, one entry at a time: an entry that covers nothing required is padding). Dangling file references fail. An entry needs all seven fields, a **Plan** from `verify | replace | sandbox | accept`, and `accept` needs `because ...`. **Assumes** must link a written contract or say `no written contract` (counted as a gap); **Test** must name a test that can fail or say `none` (counted as a gap).
- Not covered by the gate (say so rather than pretend): a tool called from a script that is not on the watch-list in `scripts/trust-ledger-check.sh`, and the *quality* of an entry's prose.

The count printed on every run and in the Tier 1 log `scripts/land-direct` keeps: `trust ledger: N entries (... gaps)`.

Entry format: **What** it is; **Enters** where it enters; **Assumes** what we assume of it (the contract); **Test** the test that can fail; **Owner**; **Plan**.

## The Lean toolchain (pinned: 4.35.0, one Lean release for the whole tree)

### T01. The Lean compiler: frontend, kernel, C emitter
- **What:** the `lean` release pinned in `lean-toolchain` and `mise.toml`: the elaborator, the kernel that checks every proof, and `EmitC`, which will turn our definitions into the C that becomes the portable artifact. A kernel soundness bug would void the proofs; an emitter bug would give the C different semantics from the Lean. Nothing proves the emitter preserves semantics.
- **Enters:** `lean-toolchain`, `mise.toml`; every `.lean` file.
- **Assumes:** the kernel is sound and `EmitC` is faithful: no written contract beyond Lean's own documentation. The shared vectors (generated by the Lean reference, run through the native library, the WebAssembly module and every binding) are the check on the emitted code; `leanchecker` and nanoda are the checks on the kernel (T02).
- **Test:** scripts/tier2.sh (leanchecker `--fresh`, nanoda); the emitter is checked only by the vectors, run through the compiled C (scripts/test_native.sh) and the WebAssembly module (scripts/test_wasm.sh).
- **Owner:** upstream Lean (leanprover/lean4); the owner pins it (CODEOWNERS: `lean-toolchain`, `mise.toml`).
- **Plan:** accept, because there is no other mature route from Lean to C, WebAssembly and the other targets and the kernel is small and independently re-checked; revisit when an extractor with a semantics-preservation proof exists.
- **Covers:** `lean-compiler` `file:lean-toolchain` `file:mise.toml`

### T02. The independent proof checkers: leanchecker, nanoda
- **What:** `leanchecker --fresh` replays every declaration in a fresh environment (guards a tampered or stale `.olean`); nanoda (`nanoda_bin`, shipped in the Lean release) re-checks the exported proof with an independent kernel implementation.
- **Enters:** `scripts/tier2.sh` (run by CI after merge); they read the build products and the `leanexport` of `LeanSse` and `LeanSseProofs`.
- **Assumes:** that two independent checkers agreeing is evidence the kernel did not mis-accept; no written contract.
- **Test:** `scripts/tier2.sh` is the test; no negative test of the checkers themselves exists here (a corrupted export that nanoda must reject is planned).
- **Owner:** upstream Lean; the owner approves the tier script (CODEOWNERS via the protected set).
- **Plan:** verify. Add a negative self-test (a corrupted export must fail nanoda).
- **Covers:** `tool:leanchecker` `tool:nanoda`

### T03. The Lean runtime and its headers (lean.h, libleanrt)
- **What:** the C runtime every Lean-emitted C file links: reference counting, allocation, arrays and strings, big numbers (`lean.h`, `libleanrt`). It is the lowest layer under the library's compiled code, in every binding. It is not checked by us.
- **Enters:** the Lean release pinned in `lean-toolchain`; the emitted C of `LeanSse` includes `lean.h`; for WebAssembly and the freestanding build the small runtime of T10 replaces it.
- **Assumes:** the runtime implements Lean's object model correctly; no written contract.
- **Test:** none of ours: the shipped native and WebAssembly builds replace it with the runtime of T10; it is used by the hosted test programs (tests/abi_test.c, tests/lean_layout.c) only.
- **Owner:** upstream Lean; the owner pins the version.
- **Plan:** accept, because the runtime is part of the one Lean release we pin and no verified replacement exists; keep the closure `Init`-only so the part of it that runs is small (`scripts/ClosureGate.lean` forbids `Std` and `Lean` in the exports' closure).
- **Covers:** `lean-runtime`

### T04. clang and ld.lld (the compiler and linker the Lean release bundles)
- **What:** the C compiler and linker bundled in the Lean release (`bin/clang`, `bin/ld.lld`), used by `lake` and `leanc` to compile Lean's emitted C into objects and static libraries, and later to produce the WebAssembly module and the shared libraries. A miscompile here changes the program the proofs were about.
- **Enters:** `lean-toolchain` (the bundle comes with the pin); `lakefile.lean` (every `lean_lib` build).
- **Assumes:** the compiler preserves C semantics for the emitted code; no written contract.
- **Test:** the vectors run against the compiled artifact (scripts/test_native.sh, scripts/test_wasm.sh), which is the real check.
- **Owner:** upstream LLVM via the Lean release; the owner pins it.
- **Plan:** sandbox. Check the compiled artifact against the reference with the shared vectors in CI, never trust the compile; no replacement is planned.
- **Covers:** `clang-lld`

## The build and process tools

### T05. Lake and the build file
- **What:** `lake` (shipped in the Lean release) reads `lakefile.lean` and builds both libraries; the file sets `warningAsError` and `autoImplicit false` and declares the two module roots (`LeanSse`, `LeanSseProofs`), the first `Init`-only, and requires one pinned git package (T13).
- **Enters:** `lakefile.lean`; every `lake build` and `lake env lean --run` in `scripts/`.
- **Assumes:** the build builds the files that are in the tree and nothing else; the root split and the `Init`-only rule are enforced by Tier 1, not by Lake (`scripts/tier1.sh`: the import scan).
- **Test:** scripts/tier1.sh (zero-warning check with its negative case; the import scan with its negative cases).
- **Owner:** the owner (CODEOWNERS: `lakefile.lean`).
- **Plan:** accept, because Lake is the Lean toolchain's own build tool and a change to it is a toolchain change (T01).
- **Covers:** `file:lakefile.lean` `tool:lake`

### T06. mise: installs the pinned Lean release
- **What:** `mise` downloads and installs the Lean release tarball named in `mise.toml` from GitHub releases and puts it on `PATH` for `mise exec -- ...`.
- **Enters:** `mise.toml`; every script is run as `mise exec -- scripts/...`.
- **Assumes:** the tarball is the one released for that tag; no checksum is verified by us today (no written contract): this is a supply-chain gap.
- **Test:** none: nothing here can fail if the tarball were swapped (a gap, counted).
- **Owner:** the owner (`mise.toml` is in the protected set); mise is upstream.
- **Plan:** sandbox. Pin the release checksum in `mise.toml` (a lockfile) once the CI exists; until then the tarball's integrity is GitHub's.
- **Covers:** `tool:mise`

### T07. git, gh, flock, python3, cargo and the vendored lander: the process tooling
- **What:** `git` and `gh` (the red-check and the rebase and push steps of `scripts/land-direct`), `flock` (the lander's mutex), `python3` (the trust-ledger checker, the scrub gate, the workflow lint). The lander is a pinned copy of vbm-land (`scripts/land/`), which names `cargo` only in an example configuration it ships. They run on the developer's machine and in CI; none is part of any artifact.
- **Enters:** `scripts/land-direct`, `scripts/land/`, `scripts/trust_ledger.py`, `scripts/scrub.py`, `scripts/trust-ledger-check.sh`, the Tier 1 scripts.
- **Assumes:** they do what their manuals say; the self-tests of the scripts that use them (scratch repositories, a `gh` shim) are the check that our use of them is right; no written contract.
- **Test:** scripts/test_land_direct.sh, scripts/test_protected_set.sh, scripts/test_githook.sh (each runs the real script against a scratch repository).
- **Owner:** upstream tools; the owner approves the scripts (protected set).
- **Plan:** accept, because they touch the process and not the artifact: a compromised tool could land a bad change, which the gates and the owner's review of protected paths are there to catch.
- **Covers:** `tool:git` `tool:gh` `tool:flock` `tool:python3` `tool:cargo` `tool:wt`

### T08. The CI runner and workflow actions (GitHub Actions)
- **What:** `.github/workflows/core.yml` runs `scripts/tier1.sh` on every push to `main`, and `scripts/tier2.sh` every 6 hours (schedule) and on manual dispatch, on GitHub-hosted `ubuntu-latest` runners only (never self-hosted: `scripts/lint-workflows.py` fails Tier 1 on a self-hosted label, on a `pull_request_target` trigger and on any secret other than the default token). The workflow has no pull-request trigger, so a fork's code never runs with the repository's token. vbm-land's own scheduled-update workflow is not installed (it uses secrets and an unpinned action): the online drift check of the pinned lander (`scripts/land/bin/land-check --upstream`) runs in Tier 2. Third-party actions are pinned by commit sha (a comment names the tag): `actions/checkout`, `actions/cache` (restores `.lake`) and `jdx/mise-action` (installs mise and the pinned Lean). Token: the default `GITHUB_TOKEN`, `contents: read`; no secrets.
- **Enters:** `.github/workflows/`; every Tier 1 and Tier 2 run in CI. The workflows run only on GitHub: they cannot be run here.
- **Assumes:** the runner image, the pinned action commits and the cache behave as documented; a cache hit is only a speed-up (Tier 1 rebuilds with zero warnings and the gates re-derive everything), but a poisoned cache or a compromised upstream action could change what is checked. No written contract beyond GitHub's documentation: the lander's own rules (`docs/decisions/0002-land-direct.md`) read the `tier1` job as the definition of a red main.
- **Test:** none that can fail inside this repository (the workflows cannot run locally); the check that a workflow exists and is covered here is `scripts/trust-ledger-check.sh` (a `.github/workflows/*` file with no entry fails Tier 1), and `scripts/lint-workflows.py` with `scripts/test_lint_workflows.sh` checks their structure.
- **Owner:** the owner (`.github/workflows/` is in the protected set and CODEOWNERS); the actions are upstream (GitHub, jdx).
- **Plan:** sandbox. Keep the permissions read-only and secret-free; the actions are pinned to commit shas; the cache never replaces the gates.
- **Covers:** `file:.github/workflows/core.yml`

## The C interface, the runtime and the bindings

### T09. The C interface (abi/vbm_sse.c, abi/lean_mini.h, include/vbm_sse.h)
- **What:** the C edge of the library, about 100 lines. `vbm_sse_new`, `vbm_sse_feed`, `vbm_sse_free` copy a chunk into a Lean `ByteArray`, call the three Lean exports (`vbm_sse_lean_new`, `vbm_sse_lean_feed`, `vbm_sse_lean_report`) and hand the caller the bytes of the report; the reader lives in a Lean `ByteArray` payload (no `malloc`). `abi/lean_mini.h` stands in for `lean.h` in the freestanding compile (WebAssembly, the scorecard): the few names the shim uses.
- **Enters:** every binding, the native library and the WebAssembly module. It decides nothing: what an event is, and the report's layout, are Lean (`LeanSse/Abi.lean`, proved in `LeanSseProofs/Abi.lean`: `report_decodes`, `abi_feed_report`).
- **Assumes:** the contract of `include/vbm_sse.h` and of the report in `LeanSse/Abi.lean` (written contracts: argument checks, report validity until the next call, one reader per thread); that `lean_mini.h` agrees with `lean.h` on the layout of a scalar array and the boxing of a scalar (checked by `tests/lean_layout.c`); the Lean exports' ownership (`consumes the state and the chunk`, checked by the leak hook and the mutants).
- **Test:** `scripts/test_native.sh` (every vector on every cut through the built library, the argument checks, the leak hook, the layout test, and mutants of the shim that each fail), `scripts/test_wasm.sh` (the same through the WebAssembly module), `scripts/test_abi.sh` (the header, the description and the Lean documentation of the report agree, with 17 drifted variants rejected).
- **Owner:** the owner (`abi/`, `include/` are in the protected set).
- **Plan:** verify. The report is proved from the Lean side; the shim is small enough for a later proof of its own, or its replacement by a generated edge.
- **Covers:** `file:abi/vbm_sse.c`

### T10. The freestanding runtime (runtime/rt.c, runtime/include/)
- **What:** the one runtime of the WebAssembly module and of the native library, about 340 lines of C: an allocator, `mem*`, and the pieces of `libleanrt` and `Init` the generated C calls (`lean_alloc_object`, `lean_dec_ref_cold`, `lean_uint8_once_cold` (a closed `Bool`, evaluated once: the CPU test of T13), `lean_array_push`, `lean_byte_array_push`, `lean_byte_array_copy_slice`, `ByteArray.extract`, the equality of byte arrays, `List.reverse`, ...), with stub headers in place of libc's. No bignum code: a `Nat` above `LEAN_MAX_SMALL_NAT` traps (the reader's `Nat`s are lengths and offsets; the reconnection time is a `UInt64`, saturated in Lean). Single-threaded.
- **Enters:** the native library and the WebAssembly module (never the hosted build, which uses the toolchain's own runtime).
- **Assumes:** that these functions do what `lean.h` and `Init` document: no written contract beyond the Lean source of each (the same set the sibling library carries); that no `Nat` reaches a bignum; found by linking: a missing function is an undefined symbol, and `nm -u` is empty.
- **Test:** `scripts/test_native.sh` and `scripts/test_wasm.sh` run every vector through it and each carries mutants of the runtime (ByteArray push, Array push, extract, equality, free) that fail; the leak hook (live bytes flat over 2000 streams, memory not growing over 5000).
- **Owner:** the owner (`runtime/` is in the protected set).
- **Plan:** replace. A shared `vbm-rt`, with its own tests, once a second library carries a copy; until then each repository carries the copy it was tested with.
- **Covers:** `file:runtime/rt.c`

### T11. The hand-written loaders of the bindings
- **What:** `bindings/python/vbm_sse/loader.py` finds and opens `libvbm_sse` (`VBM_SSE_LIB`, the package directory, the system); `bindings/rust/loader.rs` (a build script) tells the linker where it is (`VBM_SSE_LIB_DIR`). The rest of each binding (types, prototypes, the error classes, the report reader) is generated from `abi/vbm_sse.abi.json` and checked against it on every Tier 1 run.
- **Enters:** the Python and Rust bindings.
- **Assumes:** that the file found is the library built from this tree (no check: a wrong library is a wrong answer, not an unsafe one, because the generated prototypes are the ABI's); no written contract.
- **Test:** `scripts/test_bindings.sh` loads the library it just built through each loader and runs the vectors; a loader that cannot find it fails every row.
- **Owner:** the owner.
- **Plan:** accept, because a loader decides nothing and a mistake in it is loud.
- **Covers:** `file:bindings/python/vbm_sse/loader.py` `file:bindings/rust/loader.rs`

### T12. The C, WebAssembly and binding tools
- **What:** `leanc` and the bundled `clang`, `ld.lld` (T04) build the hosted test programs and the freestanding objects; `node` (the WebAssembly module's host in `tests/wasm/`); `cargo` and `python3` (T07) run the Rust and Python bindings' tests. None is part of an artifact; each runs the vectors.
- **Enters:** `scripts/test_native.sh`, `scripts/test_wasm.sh`, `scripts/test_bindings.sh` and the scorecard's runs.
- **Assumes:** that they run the code they are given (no written contract); the tests are the check on our use of them (a corrupted row, a leak and mutants each fail the run); Tier 2 requires `node` and `cargo` (Tier 1 skips them when absent, and says so).
- **Test:** `scripts/test_wasm.sh` (a module with an import and an unresolved symbol each fail), `scripts/test_bindings.sh`.
- **Owner:** upstream tools; the owner approves the scripts (protected set).
- **Plan:** accept, because they touch the process and not the artifact.
- **Covers:** `tool:leanc` `tool:node`

### T13. The pinned verified library vbm-simd (the line-end search)
- **What:** the public vbm-simd at one commit, held by the protected lock `scripts/pinned-libs.lock` (rev and `spec_hash` over its code, its trusted C header, its clause list and its ledger; `scripts/pinned-lib.py`, `docs/decisions/0005-pinned-library.md`) and by `lakefile.lean` and `lake-manifest.json`. `LeanSse` imports `VbmSimd.Find` only and calls `VbmSimd.findFirstOf` for the first LF or CR at or after a position. The library is `Init`-only Lean, proved against its own clause in its own repository (`findFirstOf_spec`: it is the byte-at-a-time machine; standard axioms only), where its own trust ledger covers its C (the AVX2 search, the CPU test, the 8-byte load and `ctz`) and its tests (a differential test against the Lean model, a guard-page test, mutants). The closure gate counts its reached mass as specified only while the lock matches (and every module of its root is an olean of the locked checkout), prints it apart and ratchets it (`dep_mass`); its four `@[extern]` shims (`findAvx2`, `hasAvx2`, `ld64`, `ctz`) count as boundary mass. The four are the CARVE-OUTS of `scripts/carveouts.txt` (the scorecard's DECISIONS 20): outside the specified share, listed with this entry as their documented reason, protected by the lock and the protected set, their node mass ratcheted (`carveout_mass`). **Why each of the four stays trusted** (the 36 boundary nodes of the closure baseline are exactly these; the specified-share floor is an exact fraction, so a fifth shim or more boundary without more spec fails the gate): `findAvx2` (`vbm_simd_find_avx2`) is the 256-bit compare loop, and the Lean toolchain has no vector semantics to run, so its Lean body `findSpec` is its model and it is tested against it (millions of comparisons, guard pages, mutants); it is removable, `findFirstOf` falls back to the proved `findSwar`. `hasAvx2` is `cpuid`/`xgetbv`, which Lean cannot express: `findFirstOf_spec` holds for either answer, a wrong answer is a missing speed-up or an illegal-instruction fault, never a wrong result, and it is tested against the CPU's own flags. `ld64` is one 8-byte load (Lean's emitted byte-by-byte assembly is 2.4 times slower), total and zero past the end, its model `ld64Model` is proved against the byte semantics (`ld64Model_bit`). `ctz` is the count-trailing-zeros instruction, which Lean has no operator for; its model `ctzModel` is proved (`ctzModel_spec`, `ctzModel_zero`). The generated C of its modules is compiled with its header by `scripts/build_native.sh` and `scripts/build_wasm.sh` (where the target is not x86-64 with clang the header has no AVX2 body: `hasAvx2` is 0 and the proved portable search runs).
- **Enters:** `lakefile.lean`, `lake-manifest.json`, `scripts/pinned-libs.lock`, `.lake/packages/vbm-simd/` (fetched by `scripts/pinned-lib.py fetch` at the LOCK's rev, never at an unpinned one); the generated C of `VbmSimd.Spec`, `.Lanes`, `.Shims`, `.Find` in the native library and the WebAssembly module; every consumer of either.
- **Assumes:** the pinned commit is what its repository's gates passed (its Tier 1 and push CI on that commit); the proof `findFirstOf_spec` and the vbm-simd ledger entries T10 and T11 hold: no written contract beyond that repository's specification (clause VS-11) and trust ledger. The shim `vbm_simd_find_avx2` reads only inside the array and runs AVX2 only where `cpuid` and `xgetbv` say the CPU and OS do (the freestanding build has no libc, and the header uses neither). The hash covers the sources, not the built oleans: the olean check of the closure gate and the fresh CI build are what bind them.
- **Test:** `scripts/test_pinned_lib.sh` and the attacks 13a to 13j of `scripts/attacks/` (a stale rev, an edited spec file, a fork, an unlocked package, an edited lock, a removed gate step each fail), `scripts/tier1.sh` (the import scan allows `VbmSimd` and flags `VbmSimdProofs`; the closure gate's pin class and ratchets with their negative self-tests), `scripts/test_native.sh` and `scripts/test_wasm.sh` (every vector on every cut through the library built with the search), and the proof `fast_eq_parse` in `LeanSseProofs/Fast.lean`, which now rests on `VbmSimdProofs.findFirstOf_spec`.
- **Owner:** the owner (the same owner as vbm-simd); the pin changes only in a reviewed commit.
- **Plan:** verify. The kernel is proved and the shim is tested in its own repository; the part that stays trust is the shim's C and the CPU, listed there.
- **Covers:** `pin:vbm-simd` `module:VbmSimd.Find` `module:VbmSimd.Shims`
